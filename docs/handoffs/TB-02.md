# TB-02: Bulk Node Read Command

## Spec

**What:** Add a Tauri IPC command `read_nodes_bulk(names: Vec<String>)` that issues a single Zenoh GET to `nodes/bulk/read`, deserialises the `BulkReadResponse`, and returns a `HashMap<String, NodeValueEntry>` to the frontend; add a matching `useNodeBulkRead` React hook that calls it on device connect to pre-populate the live value cache.

**Why:** Individual node-value events arrive asynchronously after connect, leaving the UI stale until each node is touched; a bulk read on connect fills the `liveValues` map immediately so controls render with real values from the first render.

**Files touched:**
- `apps/genicam-studio-tauri/src-tauri/src/commands/nodes.rs` — add `read_nodes_bulk` command and `parse_bulk_response` helper
- `apps/genicam-studio-tauri/src-tauri/src/main.rs` — register `read_nodes_bulk` in `invoke_handler`
- `ui/genicam-studio-ui/src/device/useNodeBulkRead.ts` — new hook: calls `read_nodes_bulk`, merges result into `liveValues`
- `ui/genicam-studio-ui/src/device/useNodeValues.ts` — expose a setter so `useNodeBulkRead` can seed the map
- `CHANGELOG.md` — add entry under `[Unreleased]`

**Key decisions:**
- `parse_bulk_response` is extracted as a pure `fn` (not `async`) so it can be unit-tested without a Zenoh session; the command itself stays thin.
- The Zenoh GET timeout follows the existing pattern from `write_node` / `execute_command`: call `.recv_async().await` with no explicit timeout attached; a 5-second service-side timeout is documented in `docs/zenoh-api.md`. Adding a `tokio::time::timeout` wrapper around `recv_async` is noted as optional but not required for S-size scope.
- `NodeValueEntry` (already in `state/device_state.rs`) is the return type — identical shape to `NodeValueUpdate` in `genicam_zenoh_api` — so no new type is needed and the JSON contract is unchanged.
- `useNodeBulkRead` accepts `names: string[]` and an `onLoaded` callback; callers decide which names to request. This keeps the hook generic and decouples it from SFNC group config (TB-03).
- The hook is called from the existing `connect` flow in `useDevice.ts`, invoked after `connect_device` resolves with the `ParseXmlResponse`.

**Unit tests required:**
- `fn test_parse_bulk_response_happy_path` in `commands/nodes.rs` — two nodes returned, values and access modes match
- `fn test_parse_bulk_response_empty` in `commands/nodes.rs` — empty `values` map parses without error
- `fn test_parse_bulk_response_invalid_json` in `commands/nodes.rs` — malformed bytes return `Err` string

### Blocking Issues

**B-1: Wrong field path in `AppLayout.tsx` line 62 — `response.nodes_by_name` does not exist**

- File: `ui/genicam-studio-ui/src/components/Layout/AppLayout.tsx`, line 62
- `ParseXmlResponse` is `{ graph: UiGraph; xml: string; diags: Diag[]; summary: ModelSummary }`. It has no `nodes_by_name` field. `nodes_by_name` lives on the nested `UiGraph` value.
- TypeScript error (confirmed by `tsc --noEmit`): `error TS2339: Property 'nodes_by_name' does not exist on type 'ParseXmlResponse'`
- The Vite production build passes because Vite transpiles without type-checking; the error is invisible at runtime only if the `readBulk` path is never exercised while disconnected, but in practice `Object.keys(undefined)` would throw at runtime when the response type assumption is wrong.
- Fix: change line 62 from:
  ```ts
  const bulk = await readBulk(Object.keys(response.nodes_by_name));
  ```
  to:
  ```ts
  const bulk = await readBulk(Object.keys(response.graph.nodes_by_name));
  ```
