### Blocking Issues

**B-1 — React Rules of Hooks violation in `TransportLayerSection.tsx` (lines 37–39 vs 55–85)**

File: `ui/genicam-studio-ui/src/components/ImageViewer/TransportLayerSection.tsx`

The `!isConnected` early-return guard fires at line 37 before all `useState`, `useRef`, and `useEffect` calls (lines 55–85). React's Rules of Hooks require that hooks are always called unconditionally, in the same order on every render. Placing hooks after a conditional return violates this invariant.

The sibling components `ExposureGainSection.tsx` (line 81) and `ImageFormatSection.tsx` (line 156) correctly call all hooks first and place the `if (!isConnected)` guard after. `TransportLayerSection` inverts this ordering.

The build (`vite build`) and `tsc --noEmit` both passed because Vite does not enforce React hook rules at build time. The `eslint-plugin-react-hooks` rule `react-hooks/rules-of-hooks` would catch this, but only if ESLint is configured and run. The bug is real regardless: during a hot reconnect cycle where `isConnected` flips false → true the hook call count will differ between renders, causing React to throw a runtime error.

Fix: move all `useState`, `useRef`, and `useEffect` declarations to the top of the function body, before the `if (!isConnected)` guard — matching the pattern in `ExposureGainSection.tsx`. The initial values of the `useState` calls that depend on `packetSizeC.min` / `interPacketDelayC.min` must therefore also move above the guard; `extractNumericConstraints` and `resolveIntStep` should be called unconditionally at the top as well.

**I-1 — Test name deviation from spec: `test_formatPacketSizeLabel_min` instead of `test_formatPacketSizeLabel_zero`**

File: `ui/genicam-studio-ui/src/components/ImageViewer/transportLayerUtils.test.ts`, line 9

The Spec section of this handoff lists `test_formatPacketSizeLabel_zero` (input `0` → `"0 B"`) as a required test. The implementation substitutes `test_formatPacketSizeLabel_min` (input `220` → `"220 B"`). The implementation note explains the substitution, but the zero-value edge case is more meaningful than the min-value (both are trivially covered by the same template literal, so the min test adds no additional coverage over the typical test). The spec's zero edge case is the correct edge case to have.

Not blocking because 4 tests are present and all pass; the coverage is functionally equivalent. Recommended fix: rename the test to `test_formatPacketSizeLabel_zero` and change the input/expected to `(0)` → `"0 B"`.
