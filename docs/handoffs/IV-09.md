# IV-09: SFNC Groups Runtime Mapping

## Spec

**What:** Replace the hardcoded four-section JSX in `ControlSidebar` with a data-driven loop over `useSfncGroups()`, filtering sections by applicability against `UiGraph.nodes_by_name` and rendering them in `sfnc-groups.json` order with `default_open` from the config.

**Why:** Sections are currently hardcoded; this task makes the sidebar automatically adapt to any camera's feature set so sections only appear when the connected device actually exposes matching nodes.

**Files touched:**
- `ui/genicam-studio-ui/src/components/ImageViewer/sfncGroupUtils.ts` — create; exports pure function `isSectionApplicable(group, nodesById)`
- `ui/genicam-studio-ui/src/components/ImageViewer/sfncGroupUtils.test.ts` — create; Vitest unit tests for `isSectionApplicable` (6 cases)
- `ui/genicam-studio-ui/src/components/ImageViewer/ControlSidebar.tsx` — modify; remove `RAIL_SECTIONS` constant, add `useSfncGroups()` call, filter groups by `isSectionApplicable`, render with a `renderSectionContent` dispatch function

**Key decisions:**
- `isSectionApplicable` returns `true` when `nodesById` is empty (no device connected) so all sections are shown in disconnected state, matching the spec requirement "No device → show all".
- When `useSfncGroups()` returns `[]` (Tauri IPC not yet resolved), the expanded sidebar renders a single `"Loading controls…"` placeholder instead of duplicating the old hardcoded JSX — keeps code DRY and the loading gap is one async tick.
- `renderSectionContent` is a plain function inside the component body (not a nested component) so it can close over parent props without prop-drilling; it uses a `switch` on `group.id` and falls through to a generic placeholder for unknown ids (`"trigger"`, `"auto_functions"`, or any future group not yet implemented).
- `isSectionApplicable` accepts `Record<string, unknown>` for `nodesById` (not `Record<string, UiNode>`) to avoid importing `UiNode` into the utility file and to keep it decoupled from the graph type shape.
- The rail (collapsed sidebar) is also rebuilt from `visibleGroups` so rail icons stay consistent with the expanded view.

**Unit tests required:**
- `test_isSectionApplicable_empty_nodesById_returns_true` in `sfncGroupUtils.test.ts` — empty nodesById always yields true
- `test_isSectionApplicable_matching_node_returns_true` in `sfncGroupUtils.test.ts` — single matching node yields true
- `test_isSectionApplicable_no_matching_node_returns_false` in `sfncGroupUtils.test.ts` — no overlap yields false
- `test_isSectionApplicable_partial_match_returns_true` in `sfncGroupUtils.test.ts` — one of several features matches, yields true
- `test_isSectionApplicable_empty_features_returns_false` in `sfncGroupUtils.test.ts` — group with zero features yields false when device connected
- `test_isSectionApplicable_empty_features_empty_nodes_returns_true` in `sfncGroupUtils.test.ts` — empty features + empty nodes short-circuits to true

### Important Issues

**`useSfncGroups` has no browser/WASM fallback — ControlSidebar shows "Loading controls…" permanently in non-Tauri mode.**

File: `ui/genicam-studio-ui/src/device/useSfncGroups.ts` (line 9 — `if (!isTauri()) return;`)

When `isTauri()` is false, `useSfncGroups` returns the initial `[]` state and never populates it. `ControlSidebar` interprets `groups.length === 0` as a loading state and renders the "Loading controls…" placeholder text indefinitely. In practice `ControlSidebar` is only rendered in Tauri (Image Viewer is not wired up in the WASM demo path), so this causes no observable regression today. However the stub has no comment documenting the intentional gap, which is a maintenance hazard if the WASM path is extended.

This gap was introduced by TB-03 (not IV-09). IV-09's implementation correctly inherits the hook without worsening the situation. Flag for TB-04 or similar follow-up.

Confidence: 90% that the rendering is permanently broken in browser mode; 85% that this is out of scope for IV-09.
