# ST-01: Image Metadata Subscription

## Spec

**What:** Subscribe to `image/meta` inside the streamer so width, height, and pixel format are learned from the live Zenoh stream instead of being required CLI arguments.

**Why:** Eliminates a redundant source of truth — the Tauri backend no longer needs to read Width/Height from the node cache and pass them to the subprocess; the streamer self-configures from the same metadata the mock service already publishes.

**Files touched:**
- `apps/genicam-ws-streamer/Cargo.toml` — add `genicam_zenoh_api` workspace dependency
- `apps/genicam-ws-streamer/src/main.rs` — make `--width`/`--height` optional (with defaults 640/480); derive the `meta_key` from the image key; thread `Arc<RwLock<ImageMeta>>` into both tasks
- `apps/genicam-ws-streamer/src/zenoh_source.rs` — new `meta_subscriber` loop writes into the shared `Arc<RwLock<ImageMeta>>`; frame-encode path reads from the lock instead of a fixed `StreamSpec`; add `meta_key` field to `ZenohSourceConfig`
- `apps/genicam-ws-streamer/src/meta.rs` — (new file) pure helpers: `derive_meta_key`, `default_image_meta`, and unit-testable `parse_meta_payload`
- `apps/genicam-studio-tauri/src-tauri/src/commands/acquisition.rs` — keep passing `--width`/`--height` as the initial hint but mark them as best-effort; no structural change required

**Key decisions:**
- Use `Arc<tokio::sync::RwLock<ImageMeta>>` (not `Mutex`) because the frame encoder reads every frame while the meta subscriber writes rarely — a read-biased lock avoids contention.
- A separate Zenoh subscriber on the same session for `image/meta` is the cleanest approach; it avoids polling and requires no new channel primitives.
- `--width` and `--height` are kept as optional CLI args (defaulting to 640/480) rather than removed. The Tauri backend continues passing them so the first frame is encoded correctly even if `image/meta` is delayed.
- For ST-01 the encoder still calls `bmp.encode_gray8()` regardless of the reported pixel format. A `warn!` is emitted when `pixel_format != Mono8`. Full multi-format encoding is ST-02.
- `BmpEncoder` is re-created when the dimensions change (detected by comparing old vs new width/height in the meta subscriber). This is cheap — the header prefix is a `Vec<u8>` allocation.
- `derive_meta_key` derives the `image/meta` key from the image key by appending `/meta`, which matches `genicam_zenoh_api::keys::image_meta`. It is kept as a pure function in `meta.rs` so it can be unit-tested.

**Unit tests required:**
- `fn test_derive_meta_key_appends_meta` in `apps/genicam-ws-streamer/src/meta.rs` — verifies the key derivation for a representative device ID
- `fn test_derive_meta_key_already_has_slash` in `apps/genicam-ws-streamer/src/meta.rs` — edge case: key already ends with `/`
- `fn test_parse_meta_payload_valid` in `apps/genicam-ws-streamer/src/meta.rs` — happy path: well-formed JSON round-trips through `ImageMeta`
- `fn test_parse_meta_payload_invalid_json` in `apps/genicam-ws-streamer/src/meta.rs` — malformed bytes return `Err`

### Important Issues

**1. `StreamInfo` sent to WebSocket clients is never updated when dimensions change**

File: `/Users/vitalyvorobyev/vision/genicam-studio/apps/genicam-ws-streamer/src/main.rs` line 70 / `src/ws.rs` line 90.

`StreamInfo::mono8_bmp(cli.width, cli.height)` is constructed once at startup and baked into `AppState`. When the meta subscriber updates `shared_meta` and rebuilds the `BmpEncoder`, `StreamInfo` in the WebSocket server is never updated. New WebSocket clients connecting after a dimension change receive a stale `{"type":"info","width":...,"height":...}` JSON header that no longer matches the frames being sent.

The spec requires that width/height are "learned from the live Zenoh stream" — the `BmpEncoder` correctly follows the stream, but the `info` message to clients still reports the CLI hint values, which defeats part of the stated goal. This is not a crash or data-corruption bug, but it is a correctness gap: any client that parses the `info` message to allocate a display buffer will size it incorrectly after a dimension change.

**2. Double-read / write non-atomicity in the meta subscriber dimension-change check**

File: `/Users/vitalyvorobyev/vision/genicam-studio/apps/genicam-ws-streamer/src/zenoh_source.rs` lines 95-108.

The pattern is: acquire read lock, compare dimensions, release lock, acquire write lock, write. Between the two lock acquisitions another meta message could arrive (in a future multi-threaded variant of this loop) and update `shared_meta`. In the current implementation this is harmless because the `select!` loop is single-threaded (only one arm runs at a time), so no concurrent writer exists. The code is correct today, but the comment at line 94 ("detect changes") will mislead future maintainers who might extract the subscriber into a separate task. Suggest an inline `// SAFETY: single-threaded select! loop — no concurrent writers` comment, or re-read inside the write lock to make the check-then-act atomic.
