## Spec

**What:** Fill the "Acquisition Control" sidebar section in the Image Viewer with real controls: a Start/Stop toggle button, an AcquisitionMode enum dropdown, and a frame counter display.

**Why:** IV-01 put a placeholder accordion in place; IV-02 makes it functional, completing the primary camera operation workflow and unblocking IV-03 (Exposure & Gain), which follows the same sidebar-section pattern.

**Key decisions:**
- Frame counter lives in `ImageViewer` as `useState<number>(0)`, reset to zero each time `isAcquiring` transitions `false → true`. This avoids a new hook or a ref-forwarding pattern in `ViewerCanvas`; the counter is derived purely from the WebSocket frame callback already threaded through `onFrameStats`.
- `AcquisitionMode` enum entries are read directly from `externalModel.graph.nodes_by_name["AcquisitionMode"]?.enum_entries` — no new IPC command needed. The `externalModel` prop already flows into `ImageViewer` from `AppLayout`.
- The `write_node` command for `AcquisitionMode` is invoked via `invoke("write_node", { nodeName: "AcquisitionMode", value: selectedMode })` — the same path `TauriProvider.applyNodeValue` uses — called directly from `AcquisitionSection` with a dynamic import of `@tauri-apps/api/core` behind an `isTauri()` guard. This avoids threading the full provider into the Image Viewer component tree.
- `ViewerCanvas.onFrame` is a separate callback from `onFrameStats` to keep concerns distinct: `onFrameStats` delivers the rolling fps number, `onFrame` is a lightweight "a frame arrived" signal. Both fire from the same `ws.onmessage` handler.

### Important Issues

**Prop type mismatch: `onStartAcq` / `onStopAcq` typed as `() => void` but awaited in `handleToggle`**

- `ui/genicam-studio-ui/src/components/ImageViewer/AcquisitionSection.tsx` lines 10–11 (prop interface) and lines 34–36 (`handleToggle` body)
- `ui/genicam-studio-ui/src/components/ImageViewer/ImageViewer.tsx` lines 14–15

Both the `ImageViewerProps` and `AcquisitionSectionProps` interfaces declare `onStartAcq: () => void` and `onStopAcq: () => void`. Inside `AcquisitionSection.handleToggle` these are awaited:

```ts
await onStopAcq();
// ...
await onStartAcq();
```

TypeScript permits this because `() => Promise<void>` is assignable to `() => void` (the `void` return type absorbs any value), so the build passes. However, the `busy` guard depends on the `await` completing before `setBusy(false)` runs. If a caller ever passes a true synchronous `() => void` function, `busy` is cleared immediately on the same tick and the double-click guard stops working. The types should be `() => Promise<void>` (or `() => void | Promise<void>`) to document the contract and prevent a silent regression.

Fix: change both interface declarations to `onStartAcq: () => Promise<void>` and `onStopAcq: () => Promise<void>` in both `ImageViewerProps` and `AcquisitionSectionProps`.
