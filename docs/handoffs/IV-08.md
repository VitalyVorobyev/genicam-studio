# IV-08: Color Processing section

## Spec

**What:** Add a "Color Processing" accordion section to the Image Viewer control sidebar with existence-guarded controls for BalanceRatioSelector (enum), BalanceRatio (float slider), Gamma (float slider), LUTEnable (bool toggle), and LUTSelector (enum).

**Why:** Color-sensitive imaging workflows — Bayer cameras, white-balance tuning, gamma correction — require these controls in the Image Viewer without leaving the Feature Browser.

**Key decisions:**
- `Gamma` is present in the mock fixture (`sfnc-standard.xml`, Float, 0.1–4.0); BalanceRatio and LUT nodes are absent. The Gamma slider will render against the mock service; the remaining controls appear only on real color cameras. This is correct and expected — no mock fixture changes required for IV-08.
- `formatBalanceRatioLabel` and `formatGammaLabel` use `toFixed(2)` with no unit suffix — both values are dimensionless. Keeping formatters separate from `exposureGainUtils.ts` avoids coupling unrelated concerns and matches the one-module-per-section pattern established by `triggerUtils.ts`.
- LUTEnable writes `0` or `1` (number) to `write_node`, consistent with how Boolean nodes are handled via the existing Tauri IPC command signature.
- `BalanceRatio` default fallback range is `0.0–4.0`; overridden by XML constraints when the node exists in UiGraph.
- The `color_processing` group uses `"default_open": false` — consistent with all non-essential sections (`trigger`, `transport_layer`, `auto_functions`, `image_format`).

### Important Issues

**Spec/implementation discrepancy — `LUTEnable` write value type:**
The spec document (`## Spec`, Key decisions) states "LUTEnable writes `0` or `1` (number)". The implementation at `ColorProcessingSection.tsx` line 180 passes the raw checkbox `boolean` (`e.target.checked`) directly to `writeNode`. This is **not a bug** — `write_node` on the Tauri side accepts `serde_json::Value` and a TypeScript `boolean` serialises to JSON `true`/`false`, which the mock service handles correctly. However, the spec note is misleading. The spec document should be corrected to say "LUTEnable writes a `boolean`" to match the actual implementation and the existing Tauri IPC contract. This is an Important (documentation accuracy) issue, not a code defect.
